# ForenSOC Phase 2 Design

## Overview
Phase 2 is focused on log management and detection. The goal is to build a robust pipeline that ingests raw logs, normalizes them into a common event model, applies detection rules, and generates actionable alerts.

This phase bridges foundational authentication/case/alert support with the platform's core SOC capability: event-driven detection.

## Objectives
- Ingest logs from multiple sources
- Normalize events into a shared schema
- Store both raw and normalized event data
- Implement a rule-based detection engine
- Generate alerts linked to source events and rules
- Provide search and exploration UX for logs and alerts

## Architecture

### Core services
- `LogParserService`
  - Accepts raw log files or direct text ingestion
  - Detects parser type and extracts structured fields
  - Writes raw events to `raw_events`
  - Emits normalized events to `normalized_events`

- `LogNormalizer`
  - Converts parser output into common fields
  - Fields include: timestamp, source_ip, dest_ip, username, hostname, event_type, severity, outcome, message

- `DetectionEngine`
  - Executes detection rules against normalized events
  - Supports executable rule patterns, thresholds, and duration windows
  - Emits alerts into the existing alert pipeline

- `RuleManager`
  - Stores rules in database
  - Exposes APIs for CRUD and enable/disable
  - Loads rules into the detection engine

### Data entities
- `RawEvent`
  - `id`
  - `source_type` (auth, apache, nginx, syslog, csv)
  - `raw_text`
  - `ingest_source`
  - `status` (pending, parsed, failed)
  - `metadata`
  - `created_at`

- `NormalizedEvent`
  - `id`
  - `raw_event_id`
  - `timestamp`
  - `source_ip`
  - `dest_ip`
  - `username`
  - `hostname`
  - `event_type`
  - `severity`
  - `outcome`
  - `message`
  - `created_at`

- `DetectionRule`
  - `id`
  - `name`
  - `description`
  - `severity`
  - `enabled`
  - `mitre_tactic`
  - `mitre_technique`
  - `pattern`
  - `event_type`
  - `threshold`
  - `time_window_seconds`
  - `created_at`
  - `updated_at`

- `DetectionAlert`
  - `id`
  - `alert_id` (link to core `Alert` record)
  - `normalized_event_id`
  - `rule_id`
  - `detector_name`
  - `created_at`

## API surface

### Log ingestion and event APIs
- `POST /api/logs/ingest`
  - Upload file or raw log text
  - Accepts type hints or auto-detects parser
- `GET /api/logs/raw`
  - List raw ingest records
  - Filter by source type, status, time range
- `GET /api/logs/normalized`
  - Search normalized events
  - Filter by source_ip, dest_ip, username, hostname, event_type, severity, outcome, time range
- `GET /api/logs/{event_id}`
  - Event detail with raw and normalized data

### Detection rule APIs
- `GET /api/detection/rules`
  - List available detection rules
- `POST /api/detection/rules`
  - Create a new rule
- `PUT /api/detection/rules/{rule_id}`
  - Update rule metadata or enable/disable
- `DELETE /api/detection/rules/{rule_id}`
  - Remove a rule
- `POST /api/detection/rules/{rule_id}/toggle`
  - Enable / disable rule

### Alert APIs
- `GET /api/detection/alerts`
  - List detection-generated alerts with filters
- `GET /api/detection/alerts/{id}`
  - Alert detail, source event, and matched rule
- `POST /api/detection/alerts/scan`
  - Trigger a manual historical scan of normalized events

## User experience

### Log Explorer UI
- Search by IP, username, hostname, event type, severity
- Time range selection
- Results table with quick drill-down
- Raw event preview pane
- Link from event to alerts generated by detection rules

### Detection Rules UI
- Rule list with enable/disable toggles
- Rule creation/edit form
- Rule metadata includes MITRE mapping
- Rule status and last-run summary

### Alert dashboard
- Alert counts by severity and status
- Recent detection alerts
- Drill-down into matched rule and source event
- Link alerts to cases or evidence

## Implementation plan

### Week 1: Parser and normalization foundation
- Create `raw_events` and `normalized_events` schema
- Build parser modules for auth logs, web logs, syslog, CSV
- Implement ingestion API
- Persist raw and parsed data
- Add baseline unit tests for parsers

### Week 2: Search and event storage
- Finalize normalized event schema
- Build list/search APIs for normalized events
- Add filters and pagination
- Create frontend log explorer page skeleton
- Add backend tests for query API

### Week 3: Detection engine and alerting
- Build detection rule storage and manager
- Implement detection engine with threshold rules
- Automatically generate alerts and link to normalized events
- Expose detection rule API and alerts API
- Add frontend detection rule screen and alert list integration

## Success criteria
- Logs can be ingested from at least two source formats
- Normalized events are stored and searchable via API
- Detection rules can be created and executed
- Alerts are generated from normalized events and displayed in UI
- Detection metadata includes MITRE tactic/technique mapping
